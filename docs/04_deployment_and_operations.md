# 04. 運用者権限とデプロイ設計

## この章の目的

Dockerを操作できるホストOSのユーザーをどこまで限定すべきかを判断できるようにします。あわせて、ここまでの内容を実装する順序と、最小構成の判断基準をまとめます。

```text

```

## 1. サーバー管理者がデプロイする流れ

アプリ利用者と異なり、デプロイ担当者はサーバーやCI/CDからDockerを操作します。

```text
開発者がGitへpush
  ↓
CI/CDがテストを実行
  ↓
Dockerイメージを作成
  ↓
イメージレジストリへ登録
  ↓
デプロイ処理が新しいイメージを取得
  ↓
コンテナを入れ替える
```

小規模な検証環境では、人がSSH接続して次のように実行することもできます。

```bash
git pull
docker compose up -d --build
```

ただし、複数人で運用する本番環境では、CI/CDから自動デプロイする方が操作履歴を残しやすく、人による設定差も減らせます。

### Dockerグループへの追加に注意する

ホスト側で次を実行すると、そのユーザーは`sudo`なしでDockerを操作できます。

```bash
sudo usermod -aG docker deploy_user
```

しかし、Dockerを自由に操作できるユーザーは、ホストのディレクトリをコンテナへマウントするなど、非常に強い操作が可能です。そのため、`docker`グループは実質的にroot相当として扱います。

一般利用者を`docker`グループへ追加してはいけません。Docker操作を許可するのは、信頼できる管理者または専用のデプロイユーザーに限定します。

## 2. 初心者向けの実装手順

最初から複雑な権限設計にする必要はありません。次の順序で進めると整理しやすくなります。

### Phase 1: アプリを起動する

- [ ] DjangoとPostgreSQLのコンテナを用意する
- [ ] Docker Composeで起動できるようにする
- [ ] DjangoからPostgreSQLへ接続できることを確認する

### Phase 2: コンテナを非root化する

参照: [02. コンテナの実行ユーザーと安全性](02_container_execution_and_security.md)

- [ ] Dockerfileで`appuser`を作る
- [ ] `USER appuser`を指定する
- [ ] `docker compose exec web id`で実行ユーザーを確認する
- [ ] アプリの起動と必要なファイル書き込みを確認する

### Phase 3: アプリ利用者の権限を設定する

参照: [01. 基本概念とユーザーの3層](01_overview_and_roles.md)

- [ ] 管理者・編集者・閲覧者などのロールを決める
- [ ] DjangoのGroupとPermissionを設定する
- [ ] APIやViewで権限を確認する
- [ ] 権限のない利用者が操作すると403になることをテストする

### Phase 4: 永続データを整理する

参照: [03. DBと永続データの権限設計](03_data_and_permission_design.md)

- [ ] PostgreSQLは名前付きVolumeを利用する
- [ ] アップロードファイルの保存場所を決める
- [ ] Bind Mountを使う場合はUID/GIDと書き込み権限を確認する
- [ ] 安易に`chmod 777`を使わない

### Phase 5: デプロイ権限を整理する

- [ ] Dockerを操作できる人を限定する
- [ ] 一般利用者をホストOSや`docker`グループへ追加しない
- [ ] 本番運用ではCI/CDによるデプロイを検討する
- [ ] 操作ログとデプロイ履歴を残す

## 3. 最小構成の判断基準

個人開発や小規模な業務アプリなら、まず次の構成で十分です。

```text
ホストOS
├─ Docker Compose
├─ Nginxコンテナ
│   └─ 公式イメージの既定（後述）
├─ Djangoコンテナ
│   └─ appuser（非root）
└─ PostgreSQLコンテナ
    └─ postgres（公式イメージの既定ユーザー）

Django内部
├─ 管理者
├─ 編集者
└─ 閲覧者
```

Nginx公式イメージは、ワーカープロセスをUID/GID 101へ落とす一方、masterプロセスはrootで起動します。「公式イメージを使えば非root」ではない点に注意してください。Nginxまで非rootで動かす場合は、`nginxinc/nginx-unprivileged`イメージを使うか、書き込み先ディレクトリを変更したうえで任意のUIDで実行します。

最低限、次の4点を守ります。

1. Djangoコンテナは非rootユーザーで実行する
2. アプリ利用者の権限はDjangoで管理する
3. PostgreSQLは外部へ直接公開しない
4. Dockerを操作できるホストユーザーを限定する

---

## 4. まとめ

Dockerを使ったユーザー分離は、次の3層を混ぜなければ難しくありません。

```text
アプリ利用者の権限
  → DjangoのUser・Group・Permission

コンテナ内の実行権限
  → DockerfileのUSER appuser

Dockerを操作する権限
  → ホストOS・CI/CD・dockerグループ
```

実装の中心は次の考え方です。

> 利用者の権限はDjangoで分け、Django自体はコンテナ内の非rootユーザーで動かし、Dockerを操作できる人は管理者に限定する。

最も起きやすいトラブルは、Bind Mountを使用したときのUID/GID不一致です。権限エラーが発生した場合は、まず「どの層のユーザーが、どのファイルまたは機能へアクセスしようとしているか」を切り分けます。
